# AGENT.md — Протокол Context-Free Resilience

> Системные инструкции для автономных агентов, работающих с этим репозиторием:
> LLM-сессии (CLI/GUI), воркеры poler-engine, antigravity, облачные и серверные
> инстансы. Файл живёт **в репозитории** — он переживает сброс сессии, потерю
> контекстного окна, удаление ворклога и перезагрузку виртуальной машины.
> Протокол обязателен к исполнению с первой секунды работы агента.

## 0. Машиночитаемое состояние — читать ПЕРВЫМ ДЕЛОМ

Первым действием после старта (до любых команд, до чтения README) агент читает
**`AGENT_STATE.md`** в корне репозитория. Это O(1)-восстановление вектора
движения: последний коммит, тег, статус тестов, текущая исследовательская
задача (RQ), следующая задача, блокировки. Всё остальное — лишь верификация
этого файла фактами из окружения.

Автоматизация фаз 0–3: `./scripts/agent_bootstrap.sh` (см. §4).

## 1. Фундаментальный принцип: контекст — не память

Контекстное окно LLM нестабильно и стирается при рестарте сессии. Внутренний
markdown-ворклог может быть повреждён, не загружен или удалён вместе с
виртуальной машиной. Поэтому вводится **иерархия источников истины** — при
любом конфликте побеждает старший уровень:

| Уровень | Источник | Доверие |
|---|---|---|
| 3 | Git-репозитории (локальные + удалённые), файловая система, запущенные процессы | истина, верифицировать всё остальное |
| 2 | Персистентные PTY/tmux-сессии, системные логи (`journalctl`, `dmesg`, файлы логов) | истина о ходе вычислений |
| 1 | Ворклоги, заметки, `AGENT_STATE.md` | подсказка; проверять уровнем 3 |
| 0 | Контекстное окно чата, «память» модели | **никогда не источник фактов** |

Правила:

- Агент НИКОГДА не утверждает факт о состоянии проекта из «памяти чата» —
  только после проверки уровнем 3 (`git log`, `git status`, `ls`, `ps`).
- Утверждение пользователя о состоянии — повод для проверки, а не истина:
  пользователь может смотреть на устаревшую страницу GitHub.
- Если ворклог противоречит `git log` — верит `git log`; расхождение
  фиксируется в отчёте восстановления (§7).

## 2. Персистентный терминальный слой (state reconstruction from terminals)

### 2.1. Длительная работа — только в фоновых сессиях

Любая задача длиннее ~60 секунд (сборка, `cargo test --release`, бенчмарки,
сетевые стримы, обучение, QEMU-прогоны) запускается **исключительно** в
именованной фоновой сессии, никогда — в интерактивном шелле агента:

```bash
# запуск: имя = <репо>-<задача>
tmux new-session -d -s pqr-rq13-bench 'cargo test --release 2>&1 | tee /tmp/pqr-test.log'
# опрос без блокировки (последние 100 строк):
tmux capture-pane -p -t pqr-rq13-bench -S -100
```

### 2.2. Холодный старт терминалов

При старте или «холодном перезапуске» агент обязан первым делом
проинспектировать активные фоновые терминалы и **полностью восстановить свой
вектор движения без подсказок пользователя**:

```bash
tmux ls                                   # перечень сессий
tmux capture-pane -p -t <имя> -S -100     # последние 100+ строк каждой
tmux list-panes -a -F '#{session_name}:#{window_index} #{pane_current_command} #{pane_pid}'
```

Для каждой сессии агент классифицирует состояние: RUNNING (процесс жив,
`pane_pid` существует) / FINISHED (последняя строка — результат) / FAILED
(код ошибки в последних строках) — и решает: ждать, собрать результат или
перезапустить.

### 2.3. Нулевой простой

Запущенные длительные компиляции, тесты, сетевые стримы и пайплайны **никогда
не блокируют работу агента и не прерываются сбросом чата**: агент запускает
задачу в фоне, продолжает другую работу и опрашивает `capture-pane`
периодически. Смерть чата не убивает tmux-сессию — операционная система
продолжает работать за агента.

## 3. Git-first инвариант: автоаутентификация и персистентность

### 3.1. Токен — первичный ключ

При передаче агенту персонального токена доступа агент автоматически
определяет его тип и провайдера по формату; при неоднозначности — запрашивает
уточнение, но никогда не угадывает вслепую:

| Формат | Провайдер | Инструменты |
|---|---|---|
| `ghp_…` (40 симв.) | GitHub PAT (classic) | `git`, `gh` |
| `github_pat_…` | GitHub fine-grained PAT | `git`, `gh` |
| `gho_…`, `ghu_…`, `ghs_…` | GitHub OAuth / user / server tokens | `gh` |
| `glpat-…` (дефис!) | GitLab PAT | `git`, `glab` |
| `gtc_…` | Gitea token | `git`, `tea` |
| `xoxb-…`, `xoxp-…` | Slack (не git!) | — |
| `ssh-ed25519 …`, `ssh-rsa …` | SSH-ключ | `git` + SSH |
| `eyJ…` (JWT) | зависит от `aud` | спросить пользователя |
| неизвестный формат | — | **спросить, какой сервис** |

### 3.2. Самоустановка окружения (self-bootstrapping)

Агент автономно определяет недостающие инструменты CLI, устанавливает их и
настраивает конфигурацию. Порядок: проверить `command -v` → доустановить
(`apt`/`brew`/`cargo install`, tmux при отсутствии — см. §2) → настроить
`~/.gitconfig`, credential-helper, SSH-ключи → верифицировать связку
`git ls-remote`. Отсутствие инструмента — не блокер, а задача на 1 команду.

### 3.3. Безопасная персистентность прогресса

Репозиторий — вечный распределённый носитель памяти, который невозможно
потерять при сбросе локального инстанса или виртуальной машины. Поэтому:

- любое значимое изменение кода, документации или квантовых состояний
  **немедленно коммитится**;
- после зелёных тестов коммит **немедленно отправляется** (`git push`);
- в конце сессии на локальной машине не остаётся ни одного непушенного
  коммита (проверка: `git log origin/main..HEAD` пуст);
- работа ведётся в `main` для проверенных изменений; рискованные
  эксперименты — в ветке `agent/wip-<задача>`.

### 3.4. Гигиена токенов (критично)

- Токен НИКОГДА не выводится в ответах, логах, `set -x`-трассах, сообщениях
  об ошибках. В тексте — только маска: `ghp_****`.
- Токен НИКОГДА не вписывается в remote-URL (`git remote -v` должен показывать
  чистый `https://github.com/<owner>/<repo>.git`), в файлы репозитория,
  коммиты или ворклог.
- Хранение — только через credential-helper, подача — через stdin:
  ```bash
  printf 'protocol=https\nhost=github.com\nusername=x-access-token\npassword=%s\n' "$TOKEN" \
    | git credential approve
  ```
- Токен, опубликованный в чате/логе/файле, считается **скомпрометированным**:
  агент обязан предупредить пользователя о необходимости отзыва и до отзыва
  использовать его только для операций, которые пользователь явно запросил.
- Срок жизни токена в чате — до конца сессии; ротация по умолчанию 30 дней.

## 4. Алгоритм холодного старта (фазы 0–4)

Выполняется автоматически при старте новой сессии, после сброса контекста,
после перезагрузки VM. Автоматизация: `./scripts/agent_bootstrap.sh` —
собирает всё в один Markdown-отчёт.

**Фаза 0 — Состояние.** Прочитать `AGENT_STATE.md` (вектор движения).

**Фаза 1 — Рекогносцировка окружения.** Аудит диска (`df -h`), структуры
папок проекта, статуса git-дерева: `git status`, `git log -n 5`,
`git remote -v`; проверка инструментов (`git`, `cargo`, `tmux`, `gh`,
`python3`) с доустановкой недостающих (§3.2).

**Фаза 2 — Сканирование PTY и процессов.** Считать вывод всех активных
фоновых задач (§2.2): `tmux ls` + `capture-pane` по каждой сессии;
`ps aux` на длительные процессы (cargo, rustc, python, qemu, node).
Определить: какая задача была последней завершённой, какая выполняется сейчас.

**Фаза 3 — Подключение к удалённым ресурсам.** Проверить валидность
credentials (без печати секретов), `git fetch origin --all --tags` ПЕРВЫМ
делом — до начала любой работы (см. §5). Сравнить локальные и удалённые
ссылки, при расхождении — разрешить по §5.

**Фаза 4 — Мгновенный вход в работу.** Сформировать краткий отчёт
восстановления (§7) и продолжить выполнение задачи **без переспрашивания
пользователя**. Единственное исключение — `blocked_on` в `AGENT_STATE.md`:
тогда отчёт формулирует, чего именно не хватает.

## 5. Разрешение расхождений local vs remote

Боль «полчаса на конфликты, о которых агент не знал» лечится правилом
**fetch-before-work**: расхождение обнаруживается в фазе 3, а не в моменте
push.

```bash
git fetch origin --all --tags
git rev-list --left-right --count origin/main...HEAD   # "<behind>  <ahead>"
```

| Ситуация | Действие |
|---|---|
| `0 0` (синхронно) | работать |
| `0 N` (ahead) | работать; push после зелёных тестов |
| `N 0` (behind) | `git pull --rebase --autostash` |
| `N M` (расхождение) | `git rebase origin/main`; нетривиальные конфликты — STOP, отчёт пользователю, никакого слепого merge |
| повреждённая история | `force-push` ТОЛЬКО с явного разрешения пользователя |

Запрещено: пушить не глядя,merge вслепую, «решать» конфликт принятием одной
стороны без чтения диффа.

## 6. Протокол завершения сессии

Дополняет холодный старт — гарантирует, что следующей сессии будет что
восстанавливать:

1. Дождаться или остановить фоновые задачи; зафиксировать их результат.
2. Обновить `AGENT_STATE.md`: коммит, тег, статус тестов, `current_task`,
   `next_task`, `blocked_on`, последние строки лога.
3. Закоммитить все значимые изменения (включая ворклог-заметки сессии).
4. Запушить `main` + теги. Убедиться: `git log origin/main..HEAD` пуст.
5. Записать финальную строку в `AGENT_STATE.md` → секция «Последние сессии».

## 7. Шаблон отчёта восстановления

```markdown
## Отчёт восстановления — <дата UTC>
- Репозитории: <имя> @ <branch> <short-hash> [SYNC | AHEAD n | BEHIND n | DIRTY]
- Фоновые задачи: <сессия>: RUNNING — последняя строка: «…» | нет
- Инструменты: git ok, cargo ok, tmux ok/отсутствует (поставлен/не нужен)
- Credentials: github: валиден | отсутствует | отозван
- Вектор движения: <current_task> → <next_task> (из AGENT_STATE.md)
- Действие: продолжаю <next_task> без переспроса | заблокировано: <blocked_on>
```

## 8. Сводка MUST / NEVER

| Агент MUST | Агент NEVER |
|---|---|
| читать `AGENT_STATE.md` первым делом | считать контекст чата источником фактов |
| `git fetch` до начала любой работы | пушить/мержить не глядя в дифф |
| длительные задачи — в tmux, опрос `capture-pane` | блокироваться на часовой сборке |
| коммит сразу, push после зелёных тестов | оставлять непушенные коммиты в конце сессии |
| маскировать токен `ghp_****` | токен в remote-URL, коммите, логе, ответе |
| доустанавливать недостающие CLI сам | останавливаться из-за отсутствия инструмента |
| восстановиться и продолжить без переспроса | переспрашивать то, что написано в AGENT_STATE.md |
| предупредить об отзыве скомпрометированного токена | молча пользоваться утечённым токеном |
